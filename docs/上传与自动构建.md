# 你上传 GitHub，我继续处理构建结果

## 上传工程

创建私有仓库 SubtitleFlow，将解压后的工程内容放到仓库根目录。根目录应直接出现 pyproject.toml、src、scripts、docs 和 .github，不要额外套一层 SubtitleFlow 文件夹。

GitHub 网页上传一次有文件数量限制，推荐 GitHub Desktop 或 git 提交整个目录。macOS Finder 可按 Command+Shift+. 显示 .github；不要漏传 .github/workflows/windows.yml。不要只上传 ZIP 文件，Actions 不会自动解压 ZIP 中的工作流。模型、.work、dist 和本地虚拟环境都不用上传。

如使用终端，在解压后的工程目录执行（将仓库地址替换为你自己新建仓库的地址）：

```bash
git init -b main
git add .
git commit -m "Prepare SubtitleFlow Windows candidate"
git remote add origin 你的仓库HTTPS地址
git push -u origin main
```

## Windows 构建

main 分支推送会触发 Windows candidate build and real transcription。也可进入 Actions，选择该工作流，点击 Run workflow。使用 windows-2022 runner，下载约 600 MB 模型及固定源码，用于真实测试；模型不会写入 Git 或发行 ZIP。不要启用额外付费设置。

成功后在运行页面的 Artifacts 下载 SubtitleFlow-windows-x64-candidate。里面应有 Windows ZIP、SHA-256 和测试证据。工作流包括：MSVC 构建 FFmpeg/whisper.cpp、单元测试、Windows 原生平台插件的冻结 GUI 启动、base/small 中英文真实识别、冻结程序真实识别，最后才打 ZIP。当前工作流尚未在 Windows 实际运行。

失败时把该次运行页面链接或 build-diagnostics 文件发给我，可继续定位并修复；不要仅发送一个红叉截图。没有成功日志时，不能把仓库里的预期路径当成已生成 EXE。

## 发售之前

candidate 是候选包，不等于完成销售验收。还需 Windows 10/11 用户端检查、Qt 替换验证、最终运行库许可清单和真实售后条款；release-review.json 未完成项应保持 false。签名状态必须如实说明，若签名改变 EXE，需重跑与最终哈希绑定的测试。
